# Онлайн-обновление данных сцены V4

## Статус и область работ

План согласован для активной обработки `Обработка.d3_v4` после ревью.

Архивные версии `d3`, `d3_v2`, `d3_v3`, производные JSON и макеты данных сцены этим изменением не затрагиваются. Карточка ячейки и ВМКТ в задачу не входят и продолжают обращаться к живым WS.

## 1. Зафиксированные требования

- Источники обновляются независимо:
  - EDS — положение судов у причалов и на рейде;
  - УПП — положение вагонов;
  - УКТ — наполнение контейнерных площадок и справочник ячеек хранения.
- Для каждого источника создается отдельное предопределенное регламентное задание.
- Начальный период каждого задания — 120 секунд.
- Рекомендуемые смещения стартов: УКТ — 0 секунд, EDS — 40 секунд, УПП — 80 секунд. Смещения являются рекомендацией администраторам, а не обязательным условием поставки.
- Периоды трех заданий можно независимо менять в штатных настройках расписаний регламентных заданий.
- Для каждого раздела хранится только последний успешный снимок. История снимков не ведется.
- Снимок хранится бессрочно и не очищается по возрасту.
- Каждый успешный цикл заменяет предыдущий снимок, даже если JSON не изменился.
- При любой ошибке получения, проверки, преобразования, сериализации или записи старый успешный снимок не удаляется и не изменяется.
- Открытая форма проверяет локальные снимки раз в 20 секунд одним серверным вызовом.
- Пока совместимого успешного снимка источника нет, соответствующий слой сцены остается пустым. JSON-макеты в реальном режиме отсутствующий снимок не подменяют.
- Ошибка одного источника не мешает получению и показу данных остальных источников.
- Успешный пустой ответ источника является актуальным пустым состоянием и очищает соответствующий слой.
- При выключенной константе `ПолучениеРеальныхДанных` используются существующие демонстрационные данные из макетов.
- При повторном включении реального режима форма сразу использует последний совместимый успешный снимок.

## 2. Архитектура хранения снимков

Создать один непериодический независимый регистр сведений `СнимкиОнлайнДанныхТерминала`.

### 2.1. Ключ записи

Измерения регистра:

- `Источник` — строка со значениями `EDS`, `УПП` или `УКТ`;
- `Раздел` — строка, определяющая содержимое записи.

Допустимые пары:

| Источник | Раздел | Содержимое |
|---|---|---|
| `EDS` | `Vessels` | Сценически готовый массив судов у причалов и на рейде |
| `УПП` | `Wagons` | Сценически готовый массив вагонов |
| `УКТ` | `Placements` | Сценически готовый массив размещений контейнеров |
| `УКТ` | `Cells` | Нормализованный каталог ячеек хранения для доступности и вместимости |

В регистре одновременно находится не более четырех записей. Запись нового успешного снимка заменяет запись с той же парой `Источник + Раздел`.

### 2.2. Ресурсы записи

- `ДатаПолучения` — дата и время успешного получения с точностью до секунды; используется как версия для polling;
- `BuildId` — идентификатор сборки из `SceneManifestV4_json`;
- `ДанныеJSON` — неограниченная строка с данными раздела;
- `КоличествоОбъектов` — количество объектов раздела для диагностики;
- `ПредупрежденияJSON` — сериализованный массив предупреждений преобразования;
- `ДлительностьОбновления` — длительность успешного цикла получения и подготовки данных;
- `ХэшДанных` — хэш `ДанныеJSON` для диагностики.

Хэш не используется для пропуска записи неизменившегося JSON: каждый успешный цикл заменяет снимок и получает новую `ДатаПолучения`.

Хэш также не участвует в сравнении версий polling: версия слоя определяется только `ДатаПолучения`. Хэш служит исключительно для диагностики содержимого записи.

### 2.3. Совместимость снимка со сценой

- Регламентное задание записывает в снимок текущий `buildId` макетов V4.
- Начальная сборка и polling используют снимок только при совпадении его `BuildId` с текущим `SceneManifestV4_json.buildId`.
- Несовместимый снимок физически сохраняется, но не показывается.
- До первого успешного обновления на новой версии сцены соответствующий динамический слой пуст.

### 2.4. Атомарность

- EDS записывается одной строкой `EDS / Vessels` только после успешного получения и подготовки судов у причалов и на рейде.
- УПП записывается одной строкой `УПП / Wagons` только после успешной подготовки вагонов.
- УКТ записывает две строки `УКТ / Placements` и `УКТ / Cells` в одной транзакции и с одинаковой `ДатаПолучения`.
- Если любой запрос или подготовка раздела УКТ завершились ошибкой, обе предыдущие строки УКТ сохраняются без изменений.
- Редкая гонка ручного и регламентного запусков разрешается правилом «последняя успешная запись заменяет снимок».

`ДатаПолучения` считается достаточной версией. Из-за периода 2 минуты и запрета параллельного запуска успешные обновления одного источника в одну секунду считаются невозможным штатным сценарием.

## 3. Регламентные задания

Создать три предопределенных регламентных задания:

1. `ПолучитьНаполнениеПлощадокУКТ`;
2. `ПолучитьСудаEDS`;
3. `ПолучитьВагоныУПП`.

Настройки каждого задания:

- использование включено по умолчанию;
- период — 120 секунд;
- собственный ключ задания;
- повтор после ошибки — как у Скаут: 3 раза через 10 секунд;
- запрет одновременного выполнения двух экземпляров одного задания;
- немедленное завершение, если `ПолучениеРеальныхДанных = Ложь`;
- признак `Использование` при записи константы не переключать;
- регистрация ошибок в журнале регистрации;
- ошибка получения или преобразования не изменяет предыдущий снимок.

Расписания не связывать с константами. Три источника не объединять в одно задание. Администратор может независимо менять каждое расписание в штатном интерфейсе.

Рекомендуется разнести старты заданий в пределах двухминутного цикла на 0/40/80 секунд. Если EDT MCP не позволяет записать смещения расписаний, это не блокирует поставку: смещения документируются как рекомендация администраторам.

Проверка платформенного API подтверждает, что расписание регламентного задания задается объектом `РасписаниеРегламентногоЗадания`: свойство `ПериодПовтораВТечениеДня` принимает период в секундах, у объекта `РегламентноеЗадание` есть свойство `Расписание`. При этом назначаемые свойства ScheduledJob в текущем EDT MCP содержат только `methodName`, `key`, `use`, `predefined` и параметры повтора — способ записи вложенного расписания через `modify_metadata` не предоставлен. Существующее задание `ПолучитьТехникуСкаут` тоже не хранит расписание в `.mdo`: его расписание задано на уровне информационной базы.

Поэтому новые задания создаются через EDT MCP без расписания, а расписания (период 120 секунд и рекомендуемые смещения стартов 0/40/80 секунд) администратор задает в форме «Регламентные и фоновые задания» на уровне ИБ — так же, как сейчас задано расписание Скаут. Это фиксируется в документации и в проверке реализации.

## 4. Серверный модуль обновления

Создать серверный общий модуль `ОбновлениеОнлайнДанныхТерминала`.

Экспортные обработчики:

- `ОбновитьСудаEDS()`;
- `ОбновитьВагоныУПП()`;
- `ОбновитьНаполнениеПлощадокУКТ()`.

Последовательность каждого обработчика:

1. Проверить режим реальных данных.
2. Проверить отсутствие уже выполняющегося задания с тем же `ИмяМетода`.
3. Получить данные внешнего источника.
4. Полностью преобразовать и проверить результат.
5. Сериализовать содержимое снимка и предупреждения.
6. Рассчитать количество объектов, длительность, хэш и текущий `BuildId`.
7. Заменить запись или записи источника одной транзакцией.
8. При ошибке записать подробности в журнал регистрации, не заменяя предыдущий успешный снимок.

Механизма очистки снимков и константы срока хранения нет.

### 4.1. Контур записи и чтения

- Задания вызывают преобразования `Обработка.d3_v4`, сериализуют результат и записывают снимок. Для УКТ это внутренние функции, не экспорт `СобратьРазмещенияУКТ()`.
- `СобратьСценуИзМакетов`, polling формы и обработчики кнопок не обращаются к EDS/УПП/УКТ синхронно: они читают снимок или запускают фоновое задание.
- Преобразование внешнего ответа в объекты сцены остается в одном месте; чтение снимка не дублирует правила размещения.
- После перевода формы экспорт `СобратьРазмещенияУКТ()` больше не вызывается: его заменяют чтением снимка либо удаляют.

### 4.2. EDS

- Суда у причалов и суда на рейде входят в один раздел `EDS / Vessels`.
- Оба запроса EDS являются обязательными для успешного цикла.
- Ошибка запроса судов у причалов или запроса рейда делает весь цикл EDS неуспешным.
- При ошибке сохраняется прежний снимок целиком: и суда у причалов, и суда на рейде.
- Макеты `VesselsV4_json` и `AnchorageVessels_json` в реальный снимок не подмешиваются.
- Для задания требуется отдельный сборщик снимка EDS без fallback на демонстрационные суда.
- `EDS / Vessels` хранит один объединенный массив полных объектов сцены. Общие поля каждого судна: `id`, `kind`, `name`, `x`, `y`, `z`, `rotation`, `color`, `length`, `size`, `berthId`, `mooringSide`, `vesselType`, `refueling`.
- Для судна на рейде дополнительно сохраняются `locationType = "anchorage"`, `plannedBerthingAt`, `plannedBerthId`, `plannedLoad`, `plannedUnload`, `queuePosition`.
- Сохраняются текущие правила идентификаторов: у причала `eds-<berthId>-<sanitizedName>-<operationDate>`, у второго борта базовый идентификатор с суффиксом `-2`, на рейде `eds-anchorage-<sanitizedPortCall>`. Коллизии внутри массива разрешаются существующим числовым суффиксом.
- До выдачи числовых суффиксов входные строки стабильно сортируются по причалу, дате операции, имени судна и признаку второго борта, чтобы изменение порядка строк ответа EDS не переносило суффикс на другой объект.
- Переход одного судна с рейда к причалу меняет его `id`: рейд и причал считаются разными состояниями размещения. При обновлении старый объект рейда исчезает, а объект у причала появляется как новый.
- Отдельные некорректные строки EDS (пустое имя, неизвестный причал, отсутствующие размеры или некорректные данные рейда) пропускаются с предупреждением. Снимок остается успешным, если оба запроса EDS выполнены, формат и геометрия макетов валидны, а обработка строк завершилась без критической ошибки.
- Исходные идентификаторы EDS и IMO в объект сцены не добавляются; запросы и текущий контракт полей не расширяются.
- `EDS / Vessels` остается одним объединенным массивом, как требуется viewer. Для рейда наличие `locationType = "anchorage"` определяет источник положения; у судов у причала это поле отсутствует.

### 4.3. УКТ

- `ПолучитьЯчейкиХраненияИзУКТ` выполняется в том же задании, что и получение наполнения. Отдельного задания на справочник ячеек нет.
- В одном запуске выполняются оба запроса УКТ; новые записи создаются только при успехе обеих секций.
- Раздел `Cells` хранит нормализованные данные для `ОтметитьДоступностьЯчеек`: адрес, доступность, причину скрытия и вместимость, но не геометрию ячеек из макетов.
- Формат одной строки `Cells`: `zone`, `stack`, `row`, `disabled`, `shuttle`, `capacity`.
- Сопоставление с ячейкой сцены: `zone = zoneId`, `stack = Стек = cell.row`, `row = Ряд = cell.zoneBay`. Это действующее правило `КлючАдресаЯчейкиУКТ`, не сопоставление одноимённых полей 1:1.
- При повторе адреса `zone + stack + row` строки агрегируются до записи снимка по действующим правилам: доступная запись сильнее недоступной; `disabled` сильнее `shuttle`; `capacity` равна максимальному положительному значению.
- При открытии сцены нормализованные строки `Cells` сопоставляются с ячейками текущего макета по этому адресу. Ячейка текущего макета, отсутствующая в `Cells`, получает причину `missing`.
- Успешный ответ справочника ячеек с 0 строками либо ответ, в котором ни одна строка не сопоставилась с текущим макетом, считается защитной ошибкой данных. В этом случае не изменяются ни `УКТ / Cells`, ни `УКТ / Placements`; сохраняется предыдущий снимок УКТ целиком.
- Раздел `Placements` хранит готовые размещения контейнеров.
- Формат одного элемента `Placements` сохраняет текущий полный объект BSL без сокращения: `id`, `kind`, `siteId`, `blockId`, `zoneId`, `zoneKind`, `row`, `bay`, `tier`, `lengthFt`, `spanCells`, `cellIds`, `x`, `y`, `rotation`, `labelRotationDeg`.
- Координаты и оформление размещения рассчитываются регламентным заданием по топологии текущего макета и сохраняются в снимке. Viewer по-прежнему нормализует объект и проверяет `cellIds`; наличие вычисленных полей в снимке сохраняет действующий контракт BSL и клиентских индексов.
- Число размещений создается по значению `Ярусов` из наполнения УКТ без ограничения значениями `capacity` из `Cells` и `maxTier` макета — сохраняется текущее поведение.
- При повторе адреса `zone + stack + row` в наполнении используется первая строка; последующие строки пропускаются с предупреждением — сохраняется текущее поведение.
- Контур задания УКТ: оба запроса → нормализация `Cells` → защитная проверка сопоставления с макетом → `ОтметитьДоступностьЯчеек` и `ОтфильтроватьСкрытыеЯчейки` → `СобратьРазмещенияИзУКТ` на оставшихся ячейках. Экспорт `СобратьРазмещенияУКТ()` не вызывается: он берет нефильтрованную топологию и сам ходит в УКТ.
- `Placements` строятся по набору ячеек после применения `Cells` и существующей фильтрации: для `disabled` и `missing` размещения не создаются; для `shuttle` создаются, а сама ячейка остается серой.
- Если каталог `Cells` валиден, а запрос наполнения успешно вернул 0 занятых ячеек, это считается реальным пустым терминалом: записываются актуальный `Cells` и пустой массив `Placements`, после чего контейнеры очищаются со сцены.
- Две строки УКТ записываются атомарно и имеют одинаковую `ДатаПолучения`.
- Сборка сцены читает обе строки: скрытие `missing`/`disabled`, серые ячейки зоны шаттла, `capacity` из `КоличествоЯрусов`, затем размещения.
- Polling открытой формы применяет только `УКТ / Placements` через `updatePlacements`.
- Динамическое изменение свойств самих ячеек без пересборки сцены в задачу не входит. Раздел `Cells` применяется при следующем открытии формы или переключении `ПолучениеРеальныхДанных`.

### 4.4. УПП

- `УПП / Wagons` хранит полный текущий объект сцены `railWagon`, а не исходную строку внешнего запроса.
- Формат одного элемента: `id`, `kind = "railWagon"`, `name`, `x`, `y`, `z`, `rotation`, `color`, `size.length`, `size.width`, `wagonType`, `trainId`, `branchId`, `positionM`, `loaded`.
- `x`, `y`, `rotation` и `positionM` рассчитываются на сервере при подготовке снимка по статической железнодорожной топологии V4, ветке, направлению, порядку и длине вагона.
- В снимок записывается только массив вагонов; визуальная топология железной дороги остается в статическом макете `RailwaysV4_json`.
- При polling и начальной сборке сцены массив используется напрямую через существующую команду viewer `updateRailWagons`; повторный расчет координат не выполняется.
- Несовместимость производных координат с новой геометрией железной дороги определяется сравнением `BuildId` снимка с текущим `SceneManifestV4_json.buildId`.
- Идентификатор вагона сохраняется по текущей схеме: номер вагона из УПП. При повторе номера добавляется суффикс `-2`, `-3` и далее; перед выдачей суффиксов строки стабильно упорядочиваются по пути, порядковому номеру и номеру вагона.
- Успешный пустой ответ УПП считается реальным отсутствием вагонов: записывается новый пустой `УПП / Wagons`, а polling очищает слой вагонов.
- Строки УПП с неизвестным путем, пустым номером вагона, неположительной длиной или невозможным размещением на ветке пропускаются с предупреждением. Если внешний запрос и формат ответа успешны, снимок записывается даже если после пропуска массив вагонов пуст.
- Если состав целиком не помещается на ветке, в снимок попадает поместившаяся начальная часть состава; остальные вагоны пропускаются с предупреждением — сохраняется текущее поведение `СобратьЖелезнуюДорогу`.
- `trainId` формируется по текущей схеме `TRAIN-<branchId>`: один состав на ветку. Внешний идентификатор реального состава в запросе УПП не появляется.

## 5. Начальная сборка сцены

В режиме реальных данных `Обработка.d3_v4` не обращается к EDS, УПП и УКТ при открытии формы.

Начальная сборка читает только снимки, совместимые с текущим `BuildId`:

- совместимый снимок есть — используется его содержимое независимо от возраста;
- снимка нет или `BuildId` не совпадает — соответствующий динамический слой пуст;
- источник временно недоступен — используется последний совместимый успешный снимок;
- успешный снимок содержит пустой массив — соответствующий слой пуст;
- для УКТ раздел `Cells` применяется до фильтра скрытых ячеек, `Placements` — после, как сейчас в `СобратьСценуИзМакетов`;
- суда берутся из `EDS / Vessels` как готовый объединенный массив;
- вагоны берутся из `УПП / Wagons` как готовый массив.

JSON-макеты не подменяют отсутствующий или несовместимый снимок в режиме реальных данных. При выключенном режиме реальных данных демонстрационные JSON-макеты используются как сейчас.

При повторном включении `ПолучениеРеальныхДанных` форма пересобирается и сразу использует последний совместимый снимок.

## 6. Единый polling открытой формы

Клиентский механизм автообновления техники обобщается на все динамические источники.

`СобратьHTMLСцены()` вместе с HTML и данными сцены возвращает начальные версии уже включенных в сцену снимков: `ПериодТехники`, `ДатаEDS`, `ДатаУПП`, `ДатаУКТ`. `ПриСозданииНаСервере` переносит их в состояние формы до запуска обработчика ожидания, поэтому первый polling не передает повторно уже показанные слои.

Один обработчик ожидания раз в 20 секунд делает один серверный вызов и передает известные клиенту версии:

- период снимка Скаут;
- `ДатаПолучения` EDS;
- `ДатаПолучения` УПП;
- `ДатаПолучения` раздела `УКТ / Placements`.

Сервер за один вызов:

1. Одним запросом получает записи EDS, УПП и УКТ.
2. Отбрасывает записи с несовместимым `BuildId`.
3. Проверяет период регистра Скаут.
4. Сравнивает даты с версиями клиента.
5. Возвращает полные массивы только для изменившихся источников. Для УКТ в polling уходит только раздел `Placements`.
6. Не обращается к внешним WS.

### 6.1. Контракт серверного вызова polling

Серверный метод формы `&НаСервереБезКонтекста`, один на все источники, принимает одну структуру версий клиента и возвращает одну структуру результата.

Вход — структура `Версии`:

- `ПериодТехники` — Дата или Неопределено — известная клиенту версия снимка Скаут;
- `ДатаEDS` — Дата или Неопределено;
- `ДатаУПП` — Дата или Неопределено;
- `ДатаУКТ` — Дата или Неопределено — версия раздела `УКТ / Placements`.

Неопределено означает, что клиенту слой еще не показан (снимка не было при открытии).

Выход — структура `Результат`:

- `РежимРеальныхДанных` — Булево — текущее значение константы;
- `Техника` — структура: `ЕстьИзменения` (Булево), `ПериодСнимка` (Дата или Неопределено), `Объекты` (Массив);
- `EDS` — структура: `ЕстьИзменения`, `ДатаСнимка`, `Объекты`, `Предупреждения` (Массив строк);
- `УПП` — структура, состав как у `EDS`;
- `УКТ` — структура, состав как у `EDS`; данные раздела `Placements`.

Правила заполнения:

- `ЕстьИзменения = Истина` и непустые `Объекты` возвращаются только когда версия снимка отличается от версии клиента;
- при `ЕстьИзменения = Ложь` массив `Объекты` не заполняется данными и на клиент не передается;
- `Предупреждения` заполняются из `ПредупрежденияJSON` снимка и возвращаются только вместе с измененным слоем;
- записи с несовместимым `BuildId` считаются отсутствующими: версия слоя равна Неопределено, `ЕстьИзменения = Ложь`;
- отсутствие записи Скаут (период пуст) дает `ЕстьИзменения = Ложь`, как в текущей реализации;
- сравнение версий выполняется только по датам; хэш снимка в опросе не участвует.
- Если запись ранее показанного слоя отсутствует при polling, слой не очищается и остается на сцене: отсутствие записи не считается изменением. Очистить слой можно только новым успешным пустым снимком или пересборкой сцены.
- Если совместимый снимок старый и его `ДатаПолучения` совпадает с версией клиента, массив повторно не передается; слой остается без изменений, а дата старого снимка может отображаться в `СостояниеОбмена`.
- Ошибка чтения или разбора отдельного снимка не отменяет общий polling: соответствующая секция возвращает `Ошибка = Истина`, `ТекстОшибки`, `ЕстьИзменения = Ложь`, остальные секции обрабатываются и применяются. Поврежденный слой остается без изменений.
- Версия клиента обновляется только после успешного `ОтправитьКомандуСцене` и успешной синхронизации соответствующего индекса формы. Если viewer или индекс завершились ошибкой, версия не меняется, а следующий polling повторно возвращает полный массив слоя.
- `ДатаСнимка` каждой секции возвращается всегда, если существует совместимый снимок, даже при `ЕстьИзменения = Ложь`; массив объектов передается только при изменении версии.
- При полном сбое polling-вызова все слои и клиентские версии остаются без изменений, ошибка записывается в `СостояниеОбмена`, а следующий вызов выполняется через 20 секунд; обработчик ожидания не отключается.

Клиент независимо применяет изменения командами viewer `updateScoutVehicles`, `updateVessels`, `updateRailWagons`, `updatePlacements`. Менять `МакетJS` для этих операций не требуется.

Версия источника фиксируется на клиенте только после успешного применения команды. Ошибка одного слоя не отменяет остальные. После успешного применения слоя обновляется соответствующий клиентский индекс формы (`СинхронизироватьИндексТехники` / `Судов` / `Вагонов` / `Размещений`).

Если `РежимРеальныхДанных` в ответе отличается от состояния формы (константа переключена в другом сеансе), клиент не применяет слои из этого ответа: он перезапускает настройку автообновления и сообщает об этом в `СостояниеОбмена`. Полная пересборка сцены выполняется только по действию самого пользователя, как сейчас.

`СостояниеОбмена` остается строкой ошибок, предупреждений и служебных сообщений. Даты актуализации на него не сваливаются.

### 6.2. Даты актуализации на форме

На форму V4 выводятся четыре только для чтения поля даты:

- суда EDS — `ДатаПолучения` совместимого снимка `EDS / Vessels`;
- вагоны УПП — `ДатаПолучения` совместимого снимка `УПП / Wagons`;
- контейнеры УКТ — `ДатаПолучения` совместимого снимка `УКТ / Placements` (она же у `УКТ / Cells`);
- техника Скаут — период текущего снимка регистра `ПоложениеТехникиСкаут`.

Правила:

- поле показывает дату снимка, который сейчас на сцене, в том числе старого совместимого;
- нет совместимого снимка — поле пустое;
- дата поля обновляется в тот же момент, что и клиентская версия слоя: после успешного `ОтправитьКомандуСцене` и синхронизации индекса;
- при открытии и пересборке поля заполняются из тех же начальных версий, что возвращает `СобратьHTMLСцены()`;
- в демонстрационном режиме поля пустые и не обновляются polling;
- метаданные полей формы создаются через EDT MCP; `МакетJS` не меняется.

Защита от повторного входа обобщается на единый обработчик. Ошибка готовности HTML-плана не считается ошибкой источника. Серия ошибок опроса обработчик не отключает: текст пишется в `СостояниеОбмена`, следующий цикл через 20 секунд выполняется как обычно.

## 7. Ручное обновление

Команды формы для судов, вагонов и контейнеров остаются альтернативным ручным запуском. Они не обращаются к внешним WS из формы.

Клиентский обработчик команды вызывает одну серверную процедуру-обертку для соответствующего задания; проверка активного задания и `ФоновыеЗадания.Выполнить` находятся на сервере. Клиент не передает имя метода или произвольную строку выполнения.

При `ПолучениеРеальныхДанных = Ложь` серверная обертка не запускает фоновое задание и не меняет снимки; форма остается в демонстрационном режиме.

Доступ к ручным командам регулируется обычными правами на форму и команды. Отдельные роли или дополнительные проверки прав на источники не создаются.

Каждая команда:

- получает `ИмяМетода` соответствующего предопределенного регламентного задания из `Метаданные.РегламентныеЗадания.<ИмяЗадания>.ИмяМетода`;
- проверяет наличие активного фонового задания по отбору `ИмяМетода + СостояниеФоновогоЗадания.Активно`;
- тот же отбор по `ИмяМетода` выполняется в начале обработчика задания: ключ предопределенного задания защищает только запуски планировщика и не наследуется ручным `ФоновыеЗадания.Выполнить`;
- дублем считается только активное фоновое задание с тем же `ИмяМетода` соответствующего источника;
- если задание активно, не запускает второй экземпляр; отдельное сообщение об этом пользователю не выводится;
- иначе запускает через `ФоновыеЗадания.Выполнить(ИмяМетода,,,НаименованиеФоновогоЗадания)` тот же метод;
- четвертый параметр `ФоновыеЗадания.Выполнить` — пользовательское наименование фонового задания; третий параметр (ключ) не передается;
- не дублирует алгоритмы получения и преобразования;
- не выполняет внеочередной опрос снимков.

Ручной запуск разрешен независимо от флага `Использование` самого регламентного задания: если команда доступна пользователю и `ПолучениеРеальныхДанных = Истина`, она запускает тот же метод вручную.

Кнопка не ждет завершения и не применяет слой сразу. Данные появляются на плане после следующего цикла polling, когда `ДатаПолучения` снимка изменится. Отдельные сообщения о запуске или уже активном задании не выводятся: пользователь видит смену даты соответствующего поля актуализации.

Перед запуском и в начале обработчика задания сохраняется защита от дубля. Если из-за редкой гонки два экземпляра все же пройдут проверку, последняя успешная запись заменяет снимок.

## 8. Обрабатываемые ошибки

- Ошибка любого запроса EDS не изменяет последний успешный снимок EDS и не блокирует УПП/УКТ.
- Ошибка УПП не изменяет последний успешный снимок УПП и не блокирует EDS/УКТ.
- Ошибка любого из двух запросов УКТ не изменяет обе предыдущие строки УКТ и не блокирует EDS/УПП.
- Ошибка сериализации, валидации, расчета служебных полей или записи не создает частичный снимок.
- Успешный пустой ответ создает новый снимок с пустым массивом объектов или размещений.
- Предупреждения преобразования сохраняются вместе со снимком.
- Пароли, логины, URL и коды проверки не записываются в снимки и журнал регистрации.
- Снимок не удаляется и не скрывается из-за возраста; дата его получения показывается пользователю.
- Несовместимый по `BuildId` снимок не удаляется, но не используется сценой.

## 10. Проверка реализации

1. Проверить созданные метаданные через EDT MCP.
2. Выполнить адресную переиндексацию измененных объектов через `revalidate_objects`.
3. Проверить ошибки EDT для всех измененных и созданных объектов.
4. Убедиться, что новых ошибок относительно исходного состояния нет.
5. Проверить независимый автоматический запуск каждого задания с периодом 120 секунд.
6. Проверить рекомендуемые смещения стартов 0/40/80 секунд в документации для администратора.
7. Проверить ручной запуск из формы V4: отсутствие синхронного WS, появление слоя через polling, отсутствие второго экземпляра с тем же `ИмяМетода`; отдельное сообщение о запуске не выводится.
8. Проверить, что регистр содержит не более четырех строк с допустимыми парами `Источник + Раздел`.
9. Проверить независимое появление снимков EDS, УПП и УКТ.
10. Проверить успешный пустой ответ: соответствующий слой очищается.
11. Проверить ошибку одного WS: старый снимок сохраняется, остальные источники продолжают обновляться.
12. Проверить ошибку рейда EDS: весь цикл EDS считается неуспешным, предыдущий объединенный снимок не изменяется.
13. Проверить атомарность УКТ: ошибка `Placements` или `Cells` не изменяет ни одну из двух строк.
14. Проверить одинаковую `ДатаПолучения` строк `УКТ / Placements` и `УКТ / Cells`.
15. Проверить сохранение `BuildId`, количества, предупреждений, длительности и хэша.
16. Изменить `SceneManifestV4_json.buildId` и проверить, что старые снимки не показываются до нового успешного обновления.
17. Открыть форму V4 в тонком клиенте и проверить единый 20-секундный polling через существующий HTML-мост.
18. Проверить режим реальных данных без совместимых снимков: суда, вагоны и контейнерные размещения пусты, без подмены макетами.
19. Проверить, что сборка сцены в реальном режиме не вызывает EDS/УПП/УКТ и читает только снимки.
20. Проверить, что при открытии формы скрытие ячеек и `capacity` берутся из `УКТ / Cells`.
21. Проверить, что 20-секундный polling меняет только `УКТ / Placements` и не пересобирает свойства ячеек.
22. Проверить, что после применения слоя обновляется соответствующий индекс поиска формы.
23. Проверить, что серия ошибок polling не отключает обработчик ожидания.
24. Проверить переключение `ПолучениеРеальныхДанных`: единый обработчик останавливается и запускается заново, сохраненные снимки не удаляются.
25. Проверить демонстрационный режим: используются JSON-макеты.
26. Проверить повторное включение реального режима: сразу используются последние совместимые снимки.
27. Проверить четыре поля дат актуализации: заполнение при открытии, обновление после polling, пустые значения без снимка и в демо-режиме, дата старого совместимого снимка.
28. Проверить закрытие или переключение формы: обработчик ожидания не продолжает лишние серверные вызовы.
29. Проверить отсутствие секретов внешних систем в регистре снимков и журнале регистрации.
30. Проверить ручной запуск при `Использование = Ложь`: команда при включенных реальных данных все равно запускает метод вручную.
31. Проверить ручной запуск при `ПолучениеРеальныхДанных = Ложь`: фоновое задание не запускается, снимки не изменяются, остается демо-режим.

## 11. Учтенные стандарты

- `#std402` — периодичность не меньше минуты; начальный интервал 2 минуты; разнесение стартов 0/40/80 секунд рекомендовано администраторам.
- `#std487` — периодические проверки объединяются в один серверный вызов; форма не вызывает внешние источники.
- `#std539` — сохраняется ручной запуск из рабочего места; результат приходит через polling.
- `#std540` — отдельные предопределенные задания; при выключенной константе обработчик сразу завершается, как у Скаут. Флаг `Использование` из кода не переключается.
- `#std642` — длительные внешние обращения не выполняются синхронно из формы.
- `#std683` — текущие состояния внешних источников хранятся в непериодическом регистре сведений.
- `#std792` — строки одного успешного цикла УКТ записываются атомарно одним набором в транзакции.
